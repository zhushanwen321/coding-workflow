# 一致性对抗审查与修复循环

> 阶段 3+4。审查对象 = `git diff <基线>..HEAD` 与设计文档章节的对照。收敛方向只有两个：实现回归文档，或文档经确认后演进（进登记表）。reviewer 只报告不修改。

## 派发规模判定

- diff 总量 ≤500 行或单元 ≤2 → 单个全局 reviewer 审全部
- 否则按顶层模块分区，每区一个 reviewer（相互独立、禁止引用彼此结论，避免盲区共谋）

reviewer 同样用 general-purpose + task 内嵌指令，独立上下文。

## reviewer task 模板

```text
背景：你是对抗式一致性审查者——只报告，绝不改代码改文档。仓库 <cwd>，
  变更区间 <基线hash>..HEAD；领地映射与基线见实施计划 <绝对路径>
  （其「0 章节映射」给出设计文档各内容的实际位置）；设计文档 <绝对路径>。
目标：
1. read 实施计划的章节映射 → 按映射 read 设计文档对应节 + diff 全量。
   映射指向的节不存在或与节名原文对不上 → 立即返回「映射失效」说明，禁止按猜的节继续审
2. 逐章比对：终态是否被完整实现；机制层与实现是否一致
   （数据流/错误处理/共享接线点）；验收场景表的通过标准是否当前即可检验。
   声称事实前必须 read 原文件核实到行级；禁止凭目录名想象
3. 三分类输出，每条附 file:line 或 diff hunk 证据：
   reasonable[]    实现优于设计/合理演化且不破坏设计声明的目标 — 给理由 + 文档同步建议
   unreasonable[]  违背设计 / 遗漏未做 / 越权多做了设计外功能 — 给严重度 + 修复建议
   doc_errors[]    文档自身错了（实现是对的）— 逐条列出应修正处
4. 返回 {reasonable, unreasonable, doc_errors}（宿主无 structured-output 工具时，
   在回复中用 json 代码块返回同构对象，解析失败视同无效需重报）；
   空数组必须显式说明「在 XX 区未发现」，含糊的整体性断言无效
验收：每条结论可回溯到具体章节与文件位置
```

## 结论处理

| 分类 | 归宿 | 执行者 |
|------|------|--------|
| unreasonable | 组成修复批次 → 按单元归属：原 dev 会话仍存活则续聊定向修，否则按 execute.md「接替程序」补派并附前任证据包。修后走 execute.md 第 4 步核验 + 定向复审（只审本批影响面，不做全文重审） | subagent |
| doc_errors | 主 agent 亲自修订设计文档对应措辞，并在计划「残留风险与变更历史」节记一笔（主 agent 持有审查全景，此项不是编码，允许亲为） | 主 agent |
| reasonable | 写入计划「合理偏差登记表」节；涉及机制层面的同步设计文档「终态/机制」实际节的表述（按章节映射定位），保证后来读者不被过时描述误导 | 主 agent |

## 数字阈值 [MANDATORY]

- 审查累计 ≥3 轮仍不收敛，或 unreasonable 规模不减反增 → 整线暂停，向用户呈报残余风险矩阵，裁决后再继续
- 单条 unreasonable 的修复走「打回定向修」，超 2 轮未解决同样升级

## 清零后

更新计划状态表并 commit，转入 `flow/acceptance.md`。
