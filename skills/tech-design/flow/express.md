# 优化 agent↔用户表达流程

> 引导主 agent 借用 tech-design 的易理解性方法论，优化自己向用户的表达——当用户反馈「听不懂」「太绕」「换个说法」，或 agent 主动判断某段表述对用户不够友好时。**这不是写设计文档，不派 review agent，是一次性表达优化。**

## 什么时候用

- 用户反馈「没听懂」「太绕」「换个说法」「这个术语什么意思」
- agent 即将输出大段技术解释，预判用户可能跟不上
- agent 之前用了项目内部黑话/缩写，用户露出困惑信号

**不用**：写设计文档（走 `flow/write.md`）、审查设计文档（走 `flow/review.md`）。本流程产出的不是文档，是优化后的对话回复。

## 借用哪几条准则

tech-design 有 11 条准则，本流程只借用让表达易懂的 3 条核心：

| 准则 | 借用到表达里 | 一句话 |
|---|---|---|
| **准则 2：结论先行** | 先给结论，再给支撑 | 别让用户读三段才知道你要说啥 |
| **准则 3：使用者视角** | 站在用户的角度，说用户能看到/能操作的，不堆内部机制 | 用户不关心「config-loader 怎么解析」，关心「你做完后我会看到什么」 |
| **准则 4：抽象锚定例子** | 术语首次出现就配最小例子 | 说「缓存」就立刻配「就是浏览器记住你登录过，下次不用重登」 |

准则 1（自包含）、5-11（数据流/错误/验收/scope 等）是文档专属，**本流程不涉及**。

## Step 1：定位难懂点

找出用户卡在哪（可能多个同时存在）：

- **是结论没给？**（用户不知道你最终要干嘛）→ 用准则 2
- **是视角错位？**（你在讲内部机制，用户要的是他眼里的变化）→ 用准则 3
- **是术语没解释？**（黑话/缩写/抽象词没配例子）→ 用准则 4

## Step 2：重组表达

按定位套对应准则重写那一段/那条回复：

- **准则 2**：把结论提到最前。一句话说「我要做 X」，再给为什么、怎么做
- **准则 3**：删掉内部机制描述，换成「你做完后会看到/能做 Y」。用户视角 = 用户能感知的
- **准则 4**：每个术语/抽象词后面立刻跟一个最小例子（最好是用户已熟悉的日常类比）

## Step 3：自检后输出

重组完，过一遍：

- [ ] 结论在最前（不是埋在末尾）
- [ ] 没有未解释的术语/黑话（每个都配了例子）
- [ ] 说的是用户能感知的，不是内部机制

通过就直接回复用户。**不派 review agent**——这是一次性表达优化，不是要交付的文档。

## 与写设计文档的区别

| | 优化表达（本流程） | 写设计文档（`write.md`） |
|---|---|---|
| 产出 | 优化后的对话回复 | 一份 .md 设计文档 |
| 用哪些准则 | 2/3/4（易懂性） | 全部 11 条 |
| 走 review | 不走 | 走（派 tech-design-review） |
| 场景 | 用户说「听不懂」 | 用户说「帮我设计」 |

一句话：tech-design 的方法论不只能写文档，它的「让人易懂」内核也能用来跟用户说话。能用上就用上。
