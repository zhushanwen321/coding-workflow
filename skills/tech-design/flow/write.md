# 写设计文档流程

> 引导主 agent 按 tech-design 方法论写出设计文档。**结构标准见 `references/doc-structure.md`，写作原则见 `references/design-principles.md`。本文件只给流程步骤，不重复内容。**

## 前置：判断层性质

动手前先定两件事：

1. **本次设计的"当前层 → 下一层"是什么？** 写在文档开头显式声明（准则 10：不跨 2 层）
2. **下一层产物是什么性质？** 套 `doc-structure.md` 的层敏感调节表，确定 §3「解决方案」的侧重点
3. **本次设计是否涉及运行时行为 / 数据流 / 错误处理？** 是 → 准则 5/6/7 全部 P0 适用；否 → 可放宽

## Step 1：背景目标

写 SCQA 开篇 + 系统是什么 + 设计目标（从使用者体验倒推）+ in/out scope。

- 准则 2：标题下放一句话结论，SCQA 四句开篇
- 受众假设：假设读者会用系统但不懂内部背景，"系统是什么"要补足基本认知

## Step 2：现状与问题分析（禁止跳过）

写使用者视角的现状（真实例子）+ 真实失败模式 + 根因分析 + 物理数据流（若涉及数据）。

- 准则 3：现状放真实系统提示词/接口/界面（**取自代码不编造**）；这是读者理解方案的前提
- 准则 4：本段首次出现的抽象术语（如"元数据""契约"），立刻定义 + 绑本段例子
- 准则 5：若涉及数据流转，画磁盘→用户眼前的物理数据流图
- **禁止**上来讲"哪个文件哪个函数怎么改"（反例 2）

> 这一段最容易被偷懒跳过，也最关键。没有现状和根因，方案就是无源之水。

## Step 3：解决方案

写终态（使用者视角）+ 多方案对比 + 关键决策与权衡。

### 3.1 终态（使用者视角先行）
- 完整交互对话样例（成功路径 + 失败路径）
- 准则 6：失败路径带恢复指引（具体命令/动作）
- 终态在实现机制**之前**讲

### 3.2 多方案对比（准则 9，强制）
- ≥2 个候选方案，每个评「长期架构合理性 / 短期实现成本 / 风险」三栏
- 给明确推荐 + 推荐理由
- 被否方案说明「若用它，§2 的例子会变成什么样」

### 3.3 关键决策与权衡
- 每个决策独立成条：选择 + 被否 + 证据
- 准则 7：运行时行为断言附探针（✅已测/⛔实施期门），探针失败则断言不写
- 准则 8：遇子问题先问减法，别急着加 clever 机制

## Step 4：验收（禁止跳过）

写实施完成后在真实场景里怎么验证功能符合预期。

- **不是单测、不是 mock**：单测只验代码符合设计假设，mock 等于没验真实集成，都不回答"真实工作里好用吗"。验收用真实依赖、真实数据、真实路径
- **写清三要素**：验证场景、步骤、通过标准
- **按改动大小匹配投入**：小改动（改文案/调参数/修单点）一句话简化验证即可；大改动（新功能/行为变更/接口调整）必须写多个真实场景
- **设计阶段就定**：验收标准指导 Step 5 拆分如何分阶段验收，不是实施后补

> 这是设计最容易被偷懒跳过的一步，也是 review 重点审查项（rubric P0-13/14/15）。验收回答的是"功能在真实工作里符合预期吗"——这是设计文档最该回答的问题。

## Step 5：下一层拆分

写实施路径 + 下一层单元拆分清单 + 每项 justification + 文件改动地图（若涉及代码）+ 待验证检查点。

- 每个拆分必须说明"为什么这么拆"（供审查）
- 拆分尽量呼应 Step 4 验收：让每个拆分单元可独立验收
- 设计阶段无法确定的事诚实标"待验证"，别编

## Step 6：自检

交付前过两份清单：

1. `references/design-principles.md` 末尾的「写前自检清单」（结构和可读性 / 内容主线 / 连贯性 / 方案对比 / 完整性 / scope / 验收）
2. `review/rubric-design-doc.md` 的 P0 项（当作预审，P0 全过再交付；验收 P0-13/14/15 是重点）

**全程贯穿受众假设**：每写一段，问"一个会用系统但不懂内部背景的开发者，能读懂吗？关键概念有例子吗？"
