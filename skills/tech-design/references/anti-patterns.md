# 设计文档反模式集

> **本文件是 `design-principles.md` 的活教材。** 10 类反例归到 3 个病根，每条配真实原文 + 读者反馈 + 修正方向。全部取自一次真实重构设计文档的 4 版迭代——初稿犯了所有这些错，经对抗审查逐条暴露。
>
> **怎么用**：写设计文档前过一遍准则；卡壳或被 review 翻车时，翻本文件找同类反例。每条标注【准则 N】对应 `design-principles.md`。

---

## 三大病根（所有反例的根）

10 类反例最终归到 3 个病根，审查时按病根定位：

| 病根 | 含义 | 对应反例 | 准则 |
|---|---|---|---|
| **认知懒惰** | 靠推理声称运行时行为，不实测；或把单测/ mock 当验收，不投入真实场景验证 | 第一、九、十节 | 7/11 |
| **视角错位** | 站在写代码的人，而非读文档/用系统的人角度 | 第二、三、四节 | 3/4/5 |
| **结构失序** | 没把读者放进连贯、自包含、结论清晰的叙事 | 第五、六、七节 | 1/2/6 |

**对抗式审查的价值正在于此**：这 9 类反例全部是对抗审查（多轮独立 subagent 攻击 + 实测）逼出来的。中立审查会让它们混过去。这也是 tech-design skill 的审查 agent 必须对抗式的实战依据。

---

## 反例 1：运行时断言靠推理，实测全错【准则 7】

**这是最贵的一类——4 个版本里每一条关于运行时行为的断言，实测命中率 0%。**

| 断言（文档原文/转述） | 实测真相 |
|---|---|
| 「校验两点接入」 | 实为 **3 处**，漏了主入口 → 校验对最常用路径失效 |
| 「提取层零升级，只需改 2 行」 | 实为 **3 段重映射**，漏两处即丢字段 |
| 「`registry.getSync(name)`」 | **该 API 不存在**——凭空发明了方法签名 |
| 「schema 对象引用稳定，用 WeakMap」 | 仅短窗口稳定；跨窗口必然换新引用 |
| 「保留 `{...}` 作 YAML flow mapping」 | **5/5 真实文件 yaml.parse 全 FAIL** |
| 「WeakMap 自清理，无泄漏」 | 被强引用持有，WeakMap 退化为 Map（实测 5/5 存活） |

**病根**：每条都是「我觉得代码应该这样跑」→ 写进文档当事实 → 实测完全不是。把「应该」当「是」，不读代码/不跑探针就声称运行时行为。

**修正**：准则 7——断言附探针，先验证再声称，探针失败则断言不写进文档。

## 反例 2：重实现轻体验——上来就讲代码机制【准则 3】

**表现**：正文长这样：

> 「现状架构速览：config-loader.ts 的 safeEvalObject 用 new Function 伪 eval；workflow-list-injector 的 parseWorkflowMeta brace-match；extractMetaViaRegex → toCachedMeta → toScript 三段重映射丢字段……」

全是「改哪个文件哪个函数」，**从不展示 agent 眼里系统提示词长什么样、怎么出错**。

**读者反馈**：

> 「完全没写也没给出例子，比如：现状中，agent 看到的系统提示词如何发现资源、如何知道怎么用？……对于一个不了解项目的任务，这些东西太具体了，不是一个设计文档。」

**修正**：准则 3——先写使用者视角（真实系统提示词 + 真实失败模式 + 完整对话样例），实现机制后置为支撑。

## 反例 3：抽象术语不落地【准则 4】

**表现**：全文反复用「元数据 / meta / 资源 / 契约 / SSOT」，**从不定义「元数据」是什么、物理上在哪、对应到前面的例子是哪部分**。读者读到 §6 还不知道 §2 提的「meta」长什么样。

**读者反馈**：

> 「元数据这里，你也没写清楚这个注释块写在什么文件里？……串不起来。」
> 「元数据，没有解释元数据是什么，对应到之前给的例子里是什么。后面的内容也是同样的道理。」

**修正**：准则 4——术语首次出现定义 + 绑已展示例子；后续每节标注「影响/产出/验证 §X 例子的哪部分」。

## 反例 4：没画物理数据流【准则 5】

**表现**：写「`workflow info` 返回 parameters」「注入段有 name/description」，**从不说这些内容从哪个文件的哪个位置来**。读者无法把「注释块」「info 命令」「agent 看到的内容」串成一条链。

**读者反馈**：

> 「workflow info 的机制是读取 workflow.js 的脚本吧，然后注释块是脚本里的吧？串不起来。」

**修正**：准则 5——画一张「磁盘文件（标路径+文件内位置）→ 读取/解析 → 用户/agent 眼前」的完整数据流图。

## 反例 5：写成 delta 链，不自包含【准则 1】

**表现**：每一版正文长这样：

> 「v5 = v4 + 第二轮三方对抗审查 findings 落地……」
> 「§0 变更摘要：C1 校验改 lifecycle 单一 chokepoint（对应 R1-F1）；C2 generate 写入路径（对应 R2-P7）……」
> 「审查报告：/tmp/...v2-adversarial-review.md（R1）……」

正文满是对话上下文引用（R1-R9 编号、「v3 §4.2.1 主张被推翻」、「双独立确认」）。

**读者反馈**：

> 「这文档是啥啊？原始的设计文档呢？我们要解决的问题是什么？怎么思考分析这个问题的？解决方案有哪些？如何决策权衡利弊的？怎么给我一个没头没尾的文档啊？」

**修正**：准则 1——每版自包含（问题→分析→方案→决策→实施），变更历史/审查溯源降附录一句话，正文零「参见 vN」/零审查编号。

## 反例 6：结论不先行，证据埋没【准则 2】

**表现**：章节以「先看 4 个 parser、3 段重映射、new Function」开头，**结论（资源暴露机制不健康）埋在中间或根本没有**。大段辩解性 prose 代替结论句。

**读者反馈**：

> 「每个章节的写法，尽量遵循金字塔原理。」

**修正**：准则 2——标题下一句话结论；SCQA 开篇；每章首句加粗为该章 governing thought；归类 MECE。

---

## 反例 7：错误不给出路【准则 6】

**表现**：fail-fast 错误文案只描述「参数校验失败 + schema + 收到」，**不指向恢复动作**。agent 拿到错误仍不知下一步做什么。

**读者反馈**：

> 「各种失败的提示，如果 workflow info 命令可以解决，都可以追加上一段，用 workflow info 重新查看用法。」

**修正**：准则 6——每个失败场景配恢复指引（具体命令）；有 canonical 源则统一指向；定为贯穿原则写进设计目标。

## 反例 8：加机制而非减机制【准则 8，跨准则】

**表现**：为解决 4 个子问题，加了 4 个 clever 机制——

- WeakMap（解决 Map 泄漏）
- 自动生成示例（解决易用性）
- 错误分类 non-retryable（解决 retry 浪费）
- 空格形态匹配（解决双写）

每个机制引入**新的运行时断言**（见反例 1），全部被审查推翻。全砍后，设计更简单且正确。

**后果**：v5 反而比 v4 短 1/3，且断言全站住（砍掉了未验证的，剩下的 by construction 正确）。

**修正**：准则 8——**减法优先于加法**。遇到子问题先问「能不能砍/简化」，而非「加个 clever 机制」。clever 机制 = 新断言 = 新失败面。正确性优先靠 by construction，不靠 by clever mechanism。

## 反例 9：被翻车后仍靠推理【准则 7 的元违反】

**表现**：v2 被审查翻车（断言 0% 命中）后，写 v3 仍靠推理断言（「flow mapping 兼容」「对象引用稳定」）→ 又翻车；写 v4 又靠推理（「WeakMap 自清理」「精准匹配」）→ 再翻车。**同样的方法错误重复 4 次**，直到 v5 才立「断言附探针」纪律。

**后果**：4 轮审查才收敛，大量 token 浪费在「写断言→被推翻→改断言」循环。

**修正**：**被翻车一次就应立纪律，而非赌下一版推理会准。翻车是信号，不是噪声。**

---

## 反例 10：验收=单测或 mock，没有真实场景验证【准则 11】

**表现**：设计文档的"验收"（如果有）长这样：

> 「验收：单元测试覆盖率 ≥90%，所有 mock 测试通过。」

**全是"代码逻辑对不对"的验证，从不回答"功能在真实工作里好用吗"**。mock 掉了真实依赖等于把真实集成路径绕过——验证的是想象中的世界。单测只能证明代码符合设计者的假设，证明不了功能符合真实预期。

**读者/实施者反馈**：

> 「设计完了，但实施完怎么知道做对了？跑通单测就算成功吗？真实场景里它真的好用吗？」

**后果**：实施完只能靠运气判断成败——单测全绿但功能在真实环境崩了，是这类设计的典型翻车。与反例 1 同源：都是把"应该这样"当"就是这样"，只是反例 1 管某条行为断言，本例管整体验收。

**修正**：准则 11——验收用真实依赖、真实数据、真实路径，写明验证场景/步骤/通过标准。小改动可简化，大改动必须多个真实场景。区分"代码对不对"（单测）和"功能好不好用"（真实场景验收）。

## 自检：如何避免重蹈

写设计文档时，对照下列信号自查（任一命中即停笔修正）：

| 信号 | 对应反例 | 动作 |
|---|---|---|
| 写下「会自清理 / 在 X 之前 / 不丢类型 / 高命中」等运行时行为 | 反例 1 | 停。先跑探针或读代码核实，否则删掉这句 |
| 正文出现「vN」「Rxx-finding」「参见上版」 | 反例 5 | 删引用，重写为自包含 |
| 开头讲「哪个文件哪个函数」 | 反例 2 | 删，先写使用者看到什么 |
| 用了「元数据/契约/SSOT」却没定义、没绑例子 | 反例 3 | 加定义 + 绑已展示例子 |
| 写「A 读取 B」却没说 B 在哪个文件 | 反例 4 | 画磁盘→眼前的数据流 |
| 描述了失败却不指恢复动作 | 反例 7 | 加恢复指引 |
| 为解决子问题要加新机制 | 反例 8 | 先问能不能砍/简化 |
| 章节首句是证据不是结论 | 反例 6 | 把结论提为首句 |
| 被审查推翻过一次，下一版还在靠推理 | 反例 9 | 立即立纪律，停止推理 |
| 把"单元测试通过/覆盖率"当验收，或验收用 mock/桩/假数据 | 反例 10 | 改为真实场景验证，写明场景/步骤/通过标准 |
