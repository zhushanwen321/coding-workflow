# 设计文档结构标准

> **本文件定义一份合格技术设计文档的骨架。** 四段式结构 + 每段的「写什么 / 为什么 / 怎么写好」。骨架层无关——无论你在哪一层做设计，都套这四段；差异只在「解决方案」段的侧重点（见文末层敏感调节表）。
>
> 写作原则见 `design-principles.md`；本文件只管"结构长什么样"。

---

## 四段骨架

```
1. 背景目标       → 为什么做、要做到什么
2. 现状与问题分析 → 现在长什么样、问题根因是什么
3. 解决方案       → 改成什么样、为什么这么改（多方案对比）
4. 下一层拆分     → 怎么落地、拆成哪些下一层单元
```

**约束（准则 10）**：scope = 当前层 → 紧邻下一层，不跨 2 层。一份文档只负责"从当前层设计到下一层"。

每段都要遵守准则 2（首句结论先行）。下面逐段展开。

---

## §1 背景目标

**写什么**：SCQA 开篇 + 系统是什么 + 设计目标。

**为什么**：读者（会用系统但不懂内部背景的开发者）必须先知道"为什么做、要达到什么"，才能理解后面的方案。跳过背景直接讲方案，读者不知道你在解决什么。

**怎么写好**：
- 开篇 SCQA 四句（情境/冲突/问题/答案）——准则 2
- "系统是什么"：一两段介绍被设计的系统/模块，让没接触过的人建立基本认知
- "设计目标"：从使用者体验倒推（用户/agent 要能做到什么），不是功能清单
- 显式声明 in-scope / out-of-scope（防止 scope creep）

**正例参照**：SCQA 开篇 → `design-principles.md` 准则 2 正例；设计目标"从 agent 体验倒推四件事"。

---

## §2 现状与问题分析

**写什么**：使用者视角的现状（真实例子）+ 真实失败模式 + 根因分析 + 物理数据流（若涉及数据）。

**为什么**：这是设计文档最容易偷懒跳过的一段，也是读者最需要的——不讲清"现在有什么问题"，方案就成了无源之水。准则 3（使用者视角）和准则 5（物理数据流）的主战场。

**怎么写好**：
- **现状用真实例子**：系统提示词 / 接口请求响应 / 界面片段，**取自代码不编造**——准则 3
- **失败模式要真实**：列出当前实际怎么出错（不是想象中的），最好附触发条件
- **根因分析**：从症状挖到根因（不是停留在"用户体验差"这种表象）
- **画物理数据流**：若涉及数据流转，画从存储到用户眼前的完整数据流图——准则 5
- **抽象术语在此定义并锚定例子**：后面章节会反复用的关键概念（如"元数据""契约"），首次出现就定义 + 绑本段的例子——准则 4

**正例参照**：现状（agent 视角 + 真实系统提示词 + 失败模式 A/B/C）→ `design-principles.md` 准则 3；元数据定义 + 物理数据流图 → 准则 4/5 正例。

> **禁止**：上来就讲"config-loader.ts 的某某函数怎么改"（反例 2）。先让读者看到"使用者眼里现在长什么样、怎么出错"。

---

## §3 解决方案

**写什么**：终态（使用者视角）+ 多方案对比 + 关键决策与权衡。

**为什么**：这是设计文档的核心。要回答两个问题：① 改造后使用者眼里变成什么样（终态）；② 为什么这么改而不是别的（方案对比）。

**怎么写好**：

### 3.1 终态（使用者视角先行）
- 放完整交互对话样例（成功路径 + 失败路径）——准则 3
- 失败路径要带恢复指引——准则 6
- 终态要在实现机制**之前**讲，让读者先理解"行为设计"，再看"怎么落地"

### 3.2 多方案对比（准则 9，强制）
- **≥2 个候选方案**
- 每个方案评三栏：**长期架构合理性 / 短期实现成本 / 风险**
- 给**明确推荐 + 推荐理由**（不是"都可以"）
- 被否方案说明「若用它，§2/§3.1 的例子会变成什么样」——让取舍可感知（准则 4）
- 用表格呈现最清晰：

  | 方案 | 长期架构 | 短期成本 | 风险 | 裁决 |
  |---|---|---|---|---|
  | 方案 A（选） | ... | ... | ... | ✅ |
  | 方案 B | ... | ... | ... | ❌ |

### 3.3 关键决策与权衡
- 每个关键决策独立成条，先给选择与被否，再给证据
- 涉及运行时行为的决策，断言附探针——准则 7
- 遇到子问题先问减法——准则 8

**正例参照**：终态对话样例 → 准则 3 正例；fail-fast 带恢复 → 准则 6 正例；决策表（方案/证据/裁决/被否若用会怎样）→ 准则 9。

> **禁止**：只给一个方案（事后合理化）；方案对比只写"选了什么"不写"为何不选别的"；长期/短期成本混为一谈。

---

## §4 下一层拆分

**写什么**：实施路径 + 下一层单元拆分清单 + 每个拆分的理由。

**为什么**：设计文档要能落地。拆分清单告诉实施者"下一步做什么"，拆分理由让拆分可审查（为什么这么拆而不是别的）。

**怎么写好**：
- **实施路径**：分阶段交付，每阶段交付 §3 终态的一部分，各自可独立验证/回滚
- **拆分清单**：每个下一层单元列出 + justification（为什么这么拆）
- **文件改动地图**（若涉及代码）：新增/改写/收敛哪些模块，让实施者有清单可循
- **待验证检查点**：设计阶段无法确定的、留给实施期验证的点（诚实标注）

## 层敏感侧重点调节表

四段骨架通用，但 §3「解决方案」的**侧重点**按"本次设计的下一层性质"调节。先判断本次设计属于哪类，再套对应侧重点：

| 本次设计性质 | §3 解决方案重点 | 涉及的层敏感准则 | 典型 cw 层（仅示例） |
|---|---|---|---|
| **子目标/子系统拆分** | 划分边界、依赖关系、优先级、为什么这么切 | 1-4, 9, 10 | epic→feature |
| **需求规格** | 问题陈述、验收标准、out-of-scope、边界场景 | 1-4, 9, 10 | feature |
| **技术方案设计** | 接口先行、数据模型、错误规格、技术选型对比、物理数据流 | **全部 1-10** | slice |
| **实现计划** | 测试先行(TDD)、任务拆分、文件清单、测试范围收敛、运行时断言探针 | 1-4, **5-7**, 9, 10 | wave |

**判断方法**：问自己"本次设计的下一层产物是什么"——
- 下一层是"一组子目标/子系统" → 子目标拆分类
- 下一层是"可验收的需求集合" → 需求规格类
- 下一层是"可实现的接口/数据模型/技术方案" → 技术方案设计类（准则 5/6/7 全适用，最严格）
- 下一层是"具体的测试用例 + 代码任务" → 实现计划类

**技术方案设计类最严格**：它同时涉及数据流（准则 5）、错误处理（准则 6）、运行时行为断言（准则 7），三条层敏感准则全部 P0。其他类型可酌情放宽 5-7，但 1-4/9/10 始终必须。

> cw 的 epic/feature/slice/wave 四层仅作示例。非 cw 项目用自己的层名，按"下一层产物性质"映射到上表即可。本 skill 不依赖 cw 的层概念。
