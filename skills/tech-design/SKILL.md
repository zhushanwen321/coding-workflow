# tech-design

教**如何写好可被对抗式审查通过的技术设计文档** + **如何对抗式审查设计文档**。

层无关——无论你在哪一层做设计（需求规格 / 技术方案 / 实现计划），都套同一套方法论；差异只在"解决方案"章节的侧重点（见层适配）。

## 核心红线（7 条，详解见 references/design-principles.md）

1. **[MANDATORY] 五段骨架**：背景目标 → 现状与问题分析 → 解决方案（多方案对比）→ 验收 → 下一层拆分，缺一不可
2. **[MANDATORY] 方案对比 ≥2 个**：每个评「长期架构合理性 + 短期实现成本 + 风险」，给明确推荐
3. **[MANDATORY] 使用者视角为主线 + 抽象锚定例子**：受众假设是"会用系统但不懂内部背景的开发者"，关键概念补背景 + 最小例子
4. **[MANDATORY] 自包含 + 结论先行**：每版完整可独立读懂（不写 delta 链）；SCQA 开篇 + 每章首句结论
5. **[MANDATORY] scope = 当前层 → 紧邻下一层**，不跨 2 层设计
6. **[MANDATORY] 验收用真实场景**：不是单测、不是 mock，是实施后在真实场景验证功能符合预期；小改动可简化，大改动多场景。review 重点审查（见 `review/rubric-design-doc.md` P0-13/14/15）
7. **[MANDATORY] 涉及运行时/数据流/错误时**：运行时断言附探针、画物理数据流图、每个错误配恢复指引

> 这 7 条是写作时的红线。完整 11 条准则见 `references/design-principles.md`。

## 层适配（每一层都能用）

本 skill 不绑定任何特定的"层"概念（如 cw 的 epic/feature/slice/wave）。五段骨架任何层通用，差异只在 §3「解决方案」和 §4「验收」的侧重点——按**本次设计的下一层产物性质**调节：

| 下一层产物 | §3 解决方案重点 | §4 验收重点 | 层敏感准则(5/6/7) |
|---|---|---|---|
| 子目标/子系统 | 划分边界、依赖、优先级 | 子系统协同达成目标、边界契约真实场景成立 | 弱适用 |
| 可验收的需求集合 | 问题陈述、out-of-scope | 需求达成后真实场景验证（非单测） | 弱适用 |
| 可实现的接口/数据模型/技术方案 | 接口先行、数据模型、错误规格、选型对比、物理数据流 | 真实环境跑通关键路径（非 mock 集成） | **全适用（最严格）** |
| 具体测试用例 + 代码任务 | TDD、任务拆分、文件清单、运行时断言探针 | 端到端真实流程验证、断言探针实跑 | 全适用 |

完整调节表见 `references/doc-structure.md` 末尾。判断方法：问自己"本次设计的下一层产物是什么"，映射到上表。

## 审查：派 tech-design-review agent

审查设计文档时，派 `tech-design-review` subagent（agent 文件在 `agents/tech-design-review.md`）。它是**对抗式**审查者——默认怀疑方案不成立，专注三件事：① 逼方案自证（找反例/攻击面）② 回溯"目标→方案"因果链是否真达成 ③ 核实关键事实 + 找副作用/遗漏。

审查与修复分离：agent 只报告 must-fix/suggestion，不代改文档；主 agent 拿到报告后决定怎么改。
